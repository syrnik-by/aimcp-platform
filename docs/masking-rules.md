# Маскирование секретов на агенте-исполнителе, версия 1 (черновик для согласования с ИБ)

## Назначение

Агент-исполнитель на ВМ маскирует секреты в тексте до того, как отдать его тех.зоне. Стектрейсы и логи стендов — самый вероятный канал утечки: токены в заголовках, пароли в адресах и параметрах. Маскирование состоит из общего базового списка (этот документ) и шаблонов проекта (`data_policy.mask` в профиле, `docs/project-profile.md`).

Базовый список маскирует только секреты. Персональные данные он не трогает: проекту, у которого они попадают в логи, нужны свои шаблоны в `data_policy.mask` или `restricted: true` (логи остаются на ВМ).

## Правила

1. **Где и когда.** На ВМ, в агенте-исполнителе, на каждый текст, который уходит наверх: логи, стектрейсы, текстовые поля результатов. Тех.зона данные не маскирует.
2. **Закрыто по умолчанию.** Любая ошибка или превышение бюджета времени означает, что текст не отдаётся: `MaskingPort.mask` бросает `MaskingException`, исходный текст вызывающий наверх не отправляет. «Замаскировано, сколько успели» не бывает.
3. **Заменитель** — `[MASKED:<имя правила>]`. Имя правила у базового списка — из списка ниже, у шаблонов профиля — `project-<номер>`, номер с 1 в порядке `data_policy.mask`. По имени модель и человек видят, что здесь было, но не видят значения.
4. **Порядок.** Сначала базовые правила в порядке списка, затем шаблоны профиля. Каждое правило применяется к результату предыдущего. Повторное маскирование уже замаскированного текста ничего не меняет.
5. **Что заменяется.** Если в выражении есть именованная группа `secret`, заменяется только она (имя ключа остаётся: `password=[MASKED:secret-keyword]`), иначе всё совпадение. Пустые совпадения игнорируются.
6. **Бюджет времени.** На один вызов `mask` задаётся предельное время (настройка агента, не в коде). Регулярное выражение из репозитория проекта может зависнуть на «злом» входе; по истечении бюджета вызов прерывается (см. правило 2). Java 17 сама отсекает часть классических «катастрофических» выражений, но не все: `(.*a){25}` на тексте из 45 букв `a` и `!` упёрлось в бюджет.
7. **Размер.** Ограничение объёма логов — задача чтения логов (шаги 2.5–2.6). Маскирование ограничено только временем.
8. **Скорость базового списка.** Все квантификаторы в базовых правилах ограничены сверху: так правила не дают квадратичного времени на длинных повторяющихся входах. Новое базовое правило проверяется на злом входе (300 000 символов: цифры, `a.a.a.`, `a@a@`, `token: ` и т.п.). Первая версия `url-credentials` с неограниченной схемой (`[a-z0-9+.-]*`) на входе `a.a.a.` не укладывалась и в 20 секунд, после ограничения длины схемы — десятые доли секунды.

## Базовый список

Выражения `java.util.regex`; строка вида «имя  выражение».

```
private-key       -----BEGIN [A-Z ]{0,30}PRIVATE KEY-----[A-Za-z0-9+/=\s]*(?:-----END [A-Z ]{0,30}PRIVATE KEY-----)?
jwt               \beyJ[A-Za-z0-9_-]{5,}\.[A-Za-z0-9_-]{5,}\.[A-Za-z0-9_-]*
authorization     (?i)\b(?:proxy-)?authorization\b["']?\s*[:=]\s*["']?(?<secret>[^\r\n"']+)
bearer            (?i)\bbearer\s+(?<secret>[A-Za-z0-9._~+/=-]{8,})
url-credentials   (?i)\b[a-z][a-z0-9+.-]{0,19}://[^\s/:@]+:(?<secret>[^\s/@]+)@
secret-keyword    (?i)(?:password|passwd|pwd|secret|token|api[_-]?key|access[_-]?key)[\w-]{0,20}["']?\s*[:=]\s*["']?(?<secret>[^\s"',;&]+)
cookie            (?i)\b(?:set-)?cookie\b\s*:\s*(?<secret>[^\r\n]+)
```

Примеры (все проверены):

| Вход | Результат |
|---|---|
| `Authorization: Bearer abcdef0123456789` | `Authorization: [MASKED:authorization]` |
| `GET https://svc:p4ss@host.example.invalid/api` | `GET https://svc:[MASKED:url-credentials]@host.example.invalid/api` |
| `{"password": "hunter2", "user": "bob"}` | `{"password": "[MASKED:secret-keyword]", "user": "bob"}` |
| `authToken=abc123 apiKey: xyz789` | `authToken=[MASKED:secret-keyword] apiKey: [MASKED:secret-keyword]` |
| `Set-Cookie: JSESSIONID=abc; Path=/` | `Set-Cookie: [MASKED:cookie]` |
| `-----BEGIN PRIVATE KEY-----` и строки ключа до конца обрезанного лога | `[MASKED:private-key]` |

Не меняются: обычные строки журнала, `startMs 1760000000000`, `expected: <200> but was: <500>`, строки стектрейса `at ru.example.PaymentTest.test(PaymentTest.java:42)`.

## Что список не покрывает

- **Персональные данные** (номера карт, телефоны, адреса почты, СНИЛС, ИНН, паспорта, ФИО и др.): не маскируются. Если они попадают в логи проекта, нужны шаблоны в `data_policy.mask` или `restricted: true`. Шаблоны проекта — простые регулярные выражения без проверки найденного значения: у номера карты без контрольной суммы Луна замаскируется и любое другое длинное число.
- **Ключи доступа без слова-ключа рядом**, например голый `AKIA...` из облачных сервисов: по префиксу не ищутся. `access_key=...` и `secret=...` ловит `secret-keyword`.
- **Секреты без признака:** значение без слова-ключа рядом и без узнаваемого формата.
- **Внутренние адреса и имена хостов стендов** не маскируются: они нужны для диагностики (какой стенд не ответил). Для ИС, где адреса нельзя выносить, есть `restricted: true`.
- **Ложные срабатывания** допустимы: `maxTokens=100` будет замаскировано как `secret-keyword`. Безопасная сторона ошибки — замаскировать лишнее.

## Вопросы к ИБ

1. Состав списка: чего не хватает, что лишнее.
2. Персональные данные в логах тестов: достаточно ли для них шаблонов проекта и `restricted`.
3. Адреса и имена хостов стендов: оставлять в тексте (как сейчас) или маскировать.
