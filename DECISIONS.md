Формат записи: дата, решение, причина, отвергнутые варианты, что менять при переносе в корпоративный контур.

## D-001. Среда прототипа — одна Windows-машина
Дата: 2026-10-12
- Решение: Ollama стоит на Windows напрямую, инфраструктура (Postgres и далее) — в Docker, приложения запускаются на хосте через Gradle.
- Причина: Ollama напрямую получает доступ к GPU, приложения на хосте проще отлаживать.
- Отвергнуто: приложения в контейнерах; локальный GitLab CE (не хватит ОЗУ рядом с моделью на 18 ГБ).
- Перенос: все адреса и имена контейнеров — в конфигурации.

## D-002. Java 17, Gradle 7.3.3, граница по дате 20.02.2022
Дата: 2026-10-12

- Отвергнуто: Java 21, Spring Boot 3.x (jakarta.*).

## D-009. Java 17 через тулчейн Gradle
Дата: 2026-10-12
- Решение: в сборке `java { toolchain { languageVersion = 17 } }`. Сам Gradle запускается на любой JDK, на которой стартует (у пользователя это 11), компиляция и тесты идут на 17. Расположение JDK 17 задаётся в пользовательском `~/.gradle/gradle.properties` (`org.gradle.java.installations.paths`), в репозитории путей нет. Автоскачивание JDK выключено.
- Причина: у пользователя много проектов на разных JDK, глобальная подмена `org.gradle.java.home` сломала бы их.
- Отвергнуто: `org.gradle.java.home`; запуск Gradle только на 17.
- Перенос: PORTING: на корпоративной машине нужна JDK 17, доступная тулчейну (при необходимости — то же пользовательское свойство).

Дата: 2026-10-13
- Решение: PostgreSQL 15 (фактически 15.7) с pgvector 0.7.4, образ `pgvector/pgvector:0.7.4-pg15`, контейнер `aimcp-postgres`, том `ai-mcp-platform_pgdata`. Порт публикуется только на 127.0.0.1. - Перенос: PORTING: в корпоконтуре Postgres, скорее всего, внешний сервис, а не контейнер: приложение получит только `DB_*` из окружения. Наличие и версию pgvector там выясняет пользователь.

## D-017. Источник результатов — режим «в файл» в адаптере TestIT
Дата: 2026-10-13
- Решение: результаты прогонов получаем из адаптера TestIT. Адаптер дорабатывается: рядом с отправкой в TestIT (`HttpWriter`) пишет тот же `TestResult` в файл. Агент-исполнитель на ВМ читает файлы и приводит к нормализованному виду. Согласовано с лидами проектов и руководством.
- Причина: у адаптера самая полная модель результата (шаги, вложения, `externalId`, `workItemIds`); доработка небольшая; режим «только файл» позволяет прототипу работать без развёрнутого TestIT.
- Отвергнуто: Allure как стандарт `frame` (вариант 1), собственный сборщик в `frame` (2), API TestIT (затратно, нужна интеграция и доступность TestIT), JUnit XML Gradle как основной (нет шагов и описаний; возможен как запасной).
- Перенос: PORTING: в корпконтуре адаптер уже подключён к проектам, достаточно обновить его версию и включить режим записи в файл. Проекты без адаптера в историю не попадут, пока не подключат его.

## D-018. Контракт файла результатов v1
Дата: 2026-10-19
- Решение: формат описан в `docs/results-file-format.md`, версия 1. Один файл `<uuid>-result.json` на тест, атомарная запись через `.tmp`, UTF-8, время в миллисекундах UTC, ключи всегда присутствуют, `null` только у помеченных полей, статусы именем `ItemStatus`. Блок `run` (идентификатор прогона, версия адаптера, хост, переменные GitLab CI из белого списка) заполняется из окружения. Настройка `resultsDir` (`testit.properties`, `TMS_RESULTS_DIR`, `tmsResultsDir`).
- Причина: продюсер (адаптер) и потребители (агент-исполнитель, БД) разрабатываются отдельно и в разное время, им нужен письменный контракт с версией.
- Отвергнуто: JSONL на прогон (параллельные записи, обрыв строки); формат Allure JSON (нет `externalId` и `workItemIds`); прямая сериализация `TestResult` (Jackson плохо работает с `Throwable`, формат привязался бы к внутренней модели адаптера); составной `Writer` (порядок вызова в `stopTestCase` не позволяет писать до выхода по `DISABLED`).
- Уточнение (2026-10-19): вложения берутся из нового списка локальных путей `getLocalAttachments()`, потому что `getAttachments()` хранит идентификаторы TestIT и в режиме `DISABLED` не заполняется.
- Вернуться позже: фикстуры, номер попытки, `resultLinks`, `itemStage`, ссылки шагов, содержимое вложений (раздел «Вне версии 1» контракта). См. «Вернуться позже» в PROGRESS.md.
- Перенос: PORTING: в корпконтуре версия адаптера с режимом записи в файл выпускается как обычное обновление, проекты без адаптера в историю не попадут.

## D-019. Подключение писателя в адаптере: настройка и вложения
Дата: 2026-10-20
- Решение: настройка `resultsDir` живёт в `AdapterConfig` (источники: `testit.properties`, `TMS_RESULTS_DIR`, системное свойство `tmsResultsDir`). Запись файла вызывается в `AdapterManager.stopTestCase` после проставления `stop` и до выхода по `DISABLED` и до подмены на `BLOCKED`. Локальные пути вложений записываются в `addAttachments` всегда, до проверки режима, абсолютными и нормализованными; при некорректном пути используется исходная строка. Версия адаптера берётся из атрибута `Implementation-Version` манифеста.
- Причина: файловый режим должен работать без TestIT (режим 3) и не зависеть от рабочего каталога JVM читателя; ошибки записи и пути не должны ломать тесты проекта.
- Отвергнуто: `resultsDir` в `ClientConfiguration`; запись через `AdapterListener.beforeTestStop`; относительные пути.
- Перенос: PORTING: для работы без TestIT проекту нужен `testit.properties` (хотя бы `adapterMode=3`), потому что `AppProperties` бросает исключение, если файла нет. Для сборки адаптера на ноутбуке нужны локальные правки репозиториев (не коммитятся) и `jackson-databind-nullable` в тестовом classpath, потому что клиент TestIT подключён jar-файлом без POM.

## D-020. Хост, версия адаптера и запуск TestIT хранятся у результата теста
Дата: 2026-10-21
- Решение: в БД колонки `host`, `adapter_version` и `tms_run_id` находятся в таблице `test_result`, а не в `run`. В `run` остаются идентификатор прогона, поля CI и границы по времени. Формат файла (контракт v1) не меняется, добавлено пояснение.
- Причина: тесты одного прогона могут выполняться на разных машинах (параллельный запуск, распределение feature-файлов диспетчером `frame`), а в режиме адаптера 2 каждая JVM создаёт свой запуск в TestIT. Хост у теста нужен и для анализа: падения, привязанные к конкретной ВМ.
- Отвергнуто: хранить хост в `run` (теряется при нескольких машинах; значение зависело бы от порядка загрузки файлов); отдельная таблица исполнителей с идентификатором JVM (в файле нет идентификатора JVM, усложняет модель).
- Открыто: JVM-узлы, запускаемые диспетчером `frame` (RMI/JMS), не получают переменные CI, и каждый такой узел сгенерирует свой `runId` и создаст отдельный прогон. Диспетчер должен передавать узлам `TMS_RUN_ID` (и по возможности `CI_*`). Вернуться к этому при работе над агентом-исполнителем (этап 2) и диспетчером (этап 10).

## D-021. Идентификатор прогона: MCP_RUN_ID, CI_JOB_ID, local-<UUID>
Дата: 2026-10-21
- Решение: прогоном считается логический запуск набора тестов (регресс целиком, даже если он идёт несколькими джобами на разных ВМ). Идентификатор прогона задаёт тот, кто организует запуск, один раз и одинаковым для всех частей. Адаптер берёт `runId` по порядку: `MCP_RUN_ID` из окружения, `CI_JOB_ID`, `local-<UUID>`; значение всегда непустое. В CI формула `MCP_RUN_ID: "${CI_PIPELINE_ID}-<набор>"` пишется один раз в `.gitlab-ci.yml` или общем шаблоне. Запуск платформой и узлы диспетчера получают `MCP_RUN_ID` от оркестратора. Переменная переименована из `TMS_RUN_ID` в `MCP_RUN_ID`, потому что к TestIT она не относится (D-018, D-020 сохраняют прежнее имя в тексте как историю). В блок `ci` добавлено `jobName` (`CI_JOB_NAME`).
- Два уровня фактов: в `run` общее для всех частей (`run_id`, pipeline, commit, ref, проект, MR), у результата теста часть (`ci_job_id`, `ci_job_url`, `ci_job_name`, `host`, `adapter_version`, `tms_run_id`).
- Причина: для регресса на 4 ВМ нужна одна запись `run`, а smoke и regression должны оставаться отдельными прогонами; при этом нельзя оставлять неопределённые (`null`) идентификаторы.
- Отвергнуто: прогон = джоба CI (регресс на 4 ВМ даёт 4 записи); прогон = пайплайн (смешивает наборы и перезапуски); идентификатор `null` в локальном запуске с присвоением при сборе; UUID без префикса; общий файл-маркер `resultsDir` (хрупкий); разбор имён джоб (`regression 2/4`).
- Известное ограничение: при `maxParallelForks` локальный запуск без `MCP_RUN_ID` может дать несколько `local-<UUID>`; один идентификатор гарантирует запуск через агента-исполнителя. Перезапуск части прогона даёт повторные результаты под тем же `run_id` с другим `ci_job_id`; итоговым считается наибольший `ci_job_id`.
- Перенос: PORTING: формула `MCP_RUN_ID` добавляется в пайплайны проектов в корпоративном контуре.
- Реализация: контракт обновлён, `RunContext` и тесты адаптера обновлены (153 теста модуля зелёные).

## D-022. Схема БД истории прогонов V001
Дата: 2026-10-22
- Решение: миграция `adapters-postgres/src/main/resources/db/migration/V001__run_history.sql`, таблицы `run` (общее для прогона: проект, `run_id`, пайплайн, коммит, ветка, проект CI, номер MR, границы по времени) и `test_result` (результат теста плюс факты части прогона: джоба CI, хост, версия адаптера, запуск TestIT). Ключи `bigint generated always as identity`, уникальность `(project, run_id)` и `(run_pk, uuid)` для идемпотентной загрузки, статусы и виды ошибок `text` с `check`, шаги, ссылки, параметры и вложения в `jsonb`, метки и идентификаторы кейсов в `text[]`, длительность вычисляемая колонка. Комментарии на русском у всех таблиц и колонок (проверка: ноль колонок без комментариев), шесть индексов под историю теста, упавшие в прогоне, итоговый результат по джобе, коммит и MR.
- Причина: см. D-018, D-020, D-021; комментарии нужны для запросов к истории обычными словами (БП-8б).
- Отвергнуто: шаги отдельной таблицей (пока нет запросов по шагам, вернёмся при необходимости); enum-типы Postgres; хранение исходного документа; схема не `public`.

## D-023. Порт RunHistoryPort: правила и общий контрактный тест
Дата: 2026-10-27
- Решение: порт `RunHistoryPort` (`save`, `findRun`, `findResults`) и модель истории (records с проверкой обязательных полей в компактном конструкторе) лежат в `core`, пакет `by.syrnik.aimcp.core.history`. Правила записаны в Javadoc порта: прогон создаётся первым `save` (тогда же `receivedAt`), следующие вызовы дополняют его; результат с известным `uuid` пропускается, возвращается число новых; поля `RunInfo` — первое непустое значение; `startedAt` — самое раннее начало, `finishedAt` — самое позднее окончание; один `runId` в разных проектах — разные прогоны; `findResults` по `startedAt` (без времени — в конце), затем по `uuid`.
- Заглушка `InMemoryRunHistory` (`adapters-stub`, пакет `by.syrnik.aimcp.adapters_stub.history`) принимает `Clock`, потокобезопасна через `synchronized`.
- Контрактный тест `RunHistoryPortContract` лежит в `core/src/testFixtures` (плагин `java-test-fixtures`) и наследуется тестом каждой реализации; JDBC-адаптер (шаг 1.7) наследовал тот же класс до D-028. Ключи прогонов в тестах уникальны, поэтому очищать хранилище между тестами не нужно. Время в данных — с точностью до миллисекунды (шаги в `jsonb` хранят миллисекунды).
- Причина: правила хранилища должны одинаково выполняться в памяти и в Postgres; один набор проверок исключает расхождение реализаций. Отдельный тест на параллельную загрузку: 4 ВМ одного прогона шлют результаты одновременно, `synchronized` заглушки скрывает гонку, которую JDBC-реализация должна закрыть (`INSERT … ON CONFLICT`).
- Отвергнуто: хранить в `RunInfo`/`RunSummary` по пять полей отдельными методами `set…` (заменено одной неизменяемой записью и слиянием); `Path` для путей вложений (путь с другой машины, `String`).
- Перенос: PORTING: порт и модель переносятся без изменений; заменяется только реализация.
- Реализация на Postgres — D-024.
- Проверено 2026-10-27: 16 тестов заглушки зелёные (15 общих и 1 свой на `receivedAt` с управляемыми часами). Пять намеренных ошибок в заглушке (затирание результатов при повторном `save`, `min` вместо `max` для окончания, обновление `receivedAt` при каждом `save`, `nullsFirst` вместо `nullsLast`, замена «первое непустое» на «последнее») уронили от 1 до 4 тестов каждая; код возвращён побайтно.

## D-024. JDBC-адаптер истории прогонов
Дата: 2026-10-28
- Решение: `JdbcRunHistory` (adapters-postgres, пакет `by.syrnik.aimcp.adapters_postgres.history`) на `JdbcTemplate` и `TransactionTemplate` (spring-jdbc 5.3.15). `save` — одна транзакция: (1) `INSERT … ON CONFLICT (project, run_id) DO UPDATE` с `CASE` «первое непустое значение» и `RETURNING id`; (2) вставка результатов `ON CONFLICT (run_pk, uuid) DO NOTHING RETURNING id`, число возвращённых строк равно числу новых результатов; (3) пересчёт `run.started_at` и `run.finished_at` агрегатом `min`/`max` по `test_result`. Строка `run`, заблокированная первым запросом до конца транзакции, выстраивает параллельные загрузки частей одного прогона в очередь, отдельные блокировки не нужны.
- JSON в `jsonb`: `links`, `parameters`, `failure_suppressed` сериализует Jackson; `steps` и `attachments` собираются вручную через дерево (время в миллисекундах `startMs`/`stopMs`, вложения `[{path}]`). Причина: Jackson 2.13 без модуля `jsr310` не умеет `Instant`, а формат должен совпадать с контрактом файла и комментариями колонок.
- Чтение: `findResults` одним запросом с `JOIN` по `(project, run_id)`, сортировка `ORDER BY started_at ASC NULLS LAST, uuid COLLATE "C"` (без `"C"` порядок зависит от настроек БД и может не совпасть с порядком `String` в Java).
- Отвергнуто: цикл «прочитать текущие границы прогона и обновить» (N запросов, зависит от порядка, гонки); `DO UPDATE` для результатов (противоречит правилу «первая версия остаётся»); `jackson-datatype-jsr310` (лишняя зависимость ради одного поля); отдельная `pg_advisory_lock` (блокировка строки `run` делает то же); применение миграций приложением в этом шаге (перенесено в 1.8, где приложение стартует; тест применяет `db/migration/V*.sql` через `ScriptUtils` в UTF-8).
- Перенос: PORTING: тестов адаптера на БД в проекте больше нет (D-028), SQL и схема проверяются вручную на живой БД.
- Проверено 2026-10-28: 15 контрактных тестов зелёные на PostgreSQL 15.7 (`pgvector/pgvector:0.7.4-pg15`) в Testcontainers 1.16.3 с Docker 27.5.1. Шесть намеренных ошибок (известный `uuid` перезаписывается, `min` вместо `max` для окончания, новое значение вместо первого, `NULLS FIRST`, границы прогона не пересчитываются, вложенные шаги не пишутся) уронили от 1 до 4 тестов каждая; код возвращён побайтно. Тесты на Testcontainers сняты в D-028.
- Не покрыто тестами: `COLLATE "C"` (в контракте `uuid` из одной буквы, порядок совпадает при любой сортировке); производительность вставки (по одному запросу на результат, пачками — когда понадобится).

## D-025. Приём результатов в тех.зоне
Дата: 2026-10-28
- Решение: `POST /api/projects/{project}/results`, тело — JSON-массив документов контракта v1; ответ `200 {"received", "added", "skipped"}`, где `received = added + skipped` (в `skipped` попадают документы неизвестной версии и результаты, уже бывшие в истории). Проект берётся из адреса, не из файла. Пакет `by.syrnik.aimcp.techzone.ingest`: `ResultFileParser` (документ → `ParsedResult`), `ResultIngestService` (пачка → `RunHistoryPort`), контроллер `ResultsController`, бины в `config/HistoryConfig` (пока `InMemoryRunHistory`).
- Разбор вручную по дереву `JsonNode`, ошибки с путём к полю в формате JSON Pointer (`/test/steps/1/steps/0/status: ...`). Обязательные поля: `schemaVersion`, `run.runId`, `run.host`, `run.adapterVersion`, `test.uuid`, `externalId`, `name`, `status`, у шага `name` и `status`, у `failure` `kind` и `type`, у ссылки `url`, у вложения `path`; остальные необязательны (отсутствующие списки и словари — пустые, отсутствующий `ci` — `RunInfo` из `null`, пустой `trace` допустим). Лишние поля игнорируются (правило 9 контракта). Неизвестная `schemaVersion` — `Optional.empty()` и предупреждение в журнал, проверяется раньше остальных полей. Значения свободного текста в сообщения об ошибках не попадают (сообщение уходит клиенту и в журнал).
- Пачка принимается целиком или не принимается: сначала разбираются все документы (ошибка → `400 {"error": "документ N3: /test/uuid: ..."}`, ничего не сохранено), потом результаты группируются по `(runId, RunInfo)` и сохраняются одним `save` на группу. Ошибка хранилища — не `400`: ловится только `InvalidResultFileException`. Повтор пачки безопасен (порт идемпотентен), поэтому частичное сохранение при сбое хранилища повтором исправляется.
- Отвергнуто: разбор через привязку Jackson к записям (лишние поля и неверные типы дают исключения без пути, по ошибке в `links` и `failure` данные терялись молча); переиспользование `JsonUtils` из adapters-postgres (приложение зависело бы от детали хранилища, формат колонок не равен формату файла); страховочный `catch (NullPointerException | IllegalArgumentException)` вокруг записей домена (все требования домена проверяются явно, остаток означал бы нашу ошибку, `500` честнее); один `save` на результат (работает, но по транзакции на результат).
- Перенос: PORTING: хранилище в `HistoryConfig` — заглушка в памяти, настоящее выбирается настройкой в шаге 1.9. Эндпоинт открыт без аутентификации (открытый вопрос в PROGRESS.md), в контуре добавить проверку агента-исполнителя.
- Проверено 2026-10-28: 73 теста в `techzone` зелёные (55 парсера, включая 41 повреждённый документ с проверкой пути в сообщении; 11 сервиса на заглушке `InMemoryRunHistory`; 7 контроллера через `MockMvc` на полном контексте), `./gradlew build` зелёный вместе с 15 тестами Postgres. Руками по HTTP из собранного jar: загрузка, повтор (`added: 0`), версия 2 (`skipped`), документ без `uuid` (`400` с текстом), пустой проект (`400`), не массив (`400`). Двадцать одна намеренная ошибка в `ResultFileParser`, `ResultIngestService` и `ResultsController` (проверка версии, пустая строка, дробное время, число в списке строк, `null`-узел, неверный путь шага, потеря `RunInfo`, сохранение в цикле разбора, код ответа и др.): 20 уронили тесты сразу, одна (замена отсутствующего `trace` пустой строкой) выжила, после добавления теста `absentOrNullTraceBecomesEmpty` убита; код возвращён побайтно.

## D-027. Выбор хранилища и подключение к БД в тех.зоне
Дата: 2026-10-29
- Решение: хранилище истории выбирается свойством `aimcp.history.store` (`memory` по умолчанию, `postgres`); конфигурации `InMemoryHistoryConfig` и `PostgresHistoryConfig` включаются через `@ConditionalOnProperty`, неизвестное значение запуск останавливает (нет бина `RunHistoryPort`). `DataSource` — `HikariDataSource`, собранный вручную из `aimcp.db.url`/`user`/`password` (HikariCP 4.0.3 из BOM). Адрес собирается из `DB_HOST`, `DB_PORT`, `DB_NAME` (те же переменные, что в `.env` и `docker-compose.yml`), полный `AIMCP_DB_URL` главнее (в нём контур задаёт схему и параметры). Логин и пароль без значений по умолчанию, только из окружения.
- Автонастройка `DataSourceAutoConfiguration` исключена в `Application`: при HikariCP и spring-jdbc на пути классов она в режиме `memory` пытается создать пул из пустых `spring.datasource.*` и приложение не стартует.
- Локальные настройки читаются из `.env` в корне проекта: `spring.config.import: optional:file:.env[.properties],optional:file:../.env[.properties]` (два пути, потому что рабочий каталог зависит от способа запуска: корень проекта или каталог модуля). Переменные окружения главнее файла, отсутствие файла не ошибка. Тесты Gradle запускаются в `techzone/build/test-work`, чтобы не читать `.env` разработчика.
- Причина `.env`: Spring Boot его сам не читает (его читает только `docker compose`), а задавать переменные вручную в конфигурации запуска IDE неудобно и теряется при пересоздании конфигурации.
- Отвергнуто: `spring-boot-starter-jdbc` и `spring.datasource.*` (автонастройка конфликтует с переключателем хранилища); профили Spring (ещё одна ручная настройка запуска); переменные в конфигурации IDE.
- Перенос: PORTING: в контуре файла `.env` нет, переменные приходят из окружения; строка импорта безвредна. Формат `.env` должен быть `КЛЮЧ=значение` без кавычек и без `export`: файл читается как `.properties` (docker compose кавычки снимает, Spring нет).
- Проверено 2026-10-29: 81 тест `techzone` зелёный, в том числе сквозной на PostgreSQL 15.7 в Testcontainers (результат читается обратно через отдельный пул идентично разобранному; тест снят в D-028). Восемь намеренных ошибок в конфигурациях и yaml, включая снятие исключения автонастройки, тесты поймали; код возвращён побайтно. `.env` проверен на подделанном файле в каталоге вне проекта: чтение из корня и из каталога модуля, режим `memory` без файла, приоритет переменной ОС над файлом. Не покрыто тестами: значение по умолчанию `memory` из yaml и чтение самого `.env` (проверено вручную на jar).

## D-030. Маскирование секретов на агенте-исполнителе
Дата: 2026-11-11
- Решение: порт `MaskingPort` (`String mask(String text)`) и `MaskingException` — в `core` (пакет `by.syrnik.aimcp.core.masking`); заглушка `MarkingMaskingPort` (оборачивает текст в `MASKED(...)`, чтобы тесты видели, что текст прошёл через порт) — в `adapters-stub`; `RegexMaskingPort`, `BaseMaskingRules`, `MaskingRule`, `Deadline` — в `runner` (пакет `by.syrnik.aimcp.runner.masking`). Контракт и базовый список — `docs/masking-rules.md`.
- Базовый список — только секреты, семь правил: `private-key`, `jwt`, `authorization`, `bearer`, `url-credentials`, `secret-keyword`, `cookie`. По решению пользователя из черновика убраны все правила про персональные данные (карты, телефоны, почта, СНИЛС, ИНН, паспорт, счёт) и `aws-access-key`; вместе с ними не нужны сумма Луна и проверка найденного значения. ПДн в логах проекта закрываются шаблонами `data_policy.mask` или `restricted: true`.
- Правила работы: заменитель `[MASKED:<имя правила>]`, у шаблонов профиля `project-1`, `project-2`, ...; сначала базовые правила, потом шаблоны профиля, каждое применяется к результату предыдущего (повторное применение ничего не меняет); если в выражении есть именованная группа `secret`, заменяется только она, иначе всё совпадение; пустые совпадения игнорируются. Закрыто по умолчанию: любой сбой даёт `MaskingException`, исходный текст наверх не уходит. Сообщения исключений без фрагментов текста и без `cause`. Реализация потокобезопасна.
- Бюджет времени на вызов (больше нуля, не больше часа; задаётся при создании, в коде значения по умолчанию нет). Выражение из репозитория проекта может зависнуть на злом входе, а прерывание потока регулярное выражение не останавливает, поэтому текст передаётся движку через `CharSequence` (`Deadline`), `charAt` которого раз в 1024 чтения сверяется с часами и бросает исключение; срок проверяется и после каждого правила, так что бюджет соблюдается и на коротком тексте. Переполнение стека выражением (`(a|b)*c` на 200 000 символов), пересекающиеся группы `secret` соседних совпадений и любой другой сбой превращаются в `MaskingException`.
- Скорость базового списка: все квантификаторы ограничены сверху. Проверка на злых входах по 300 КБ нашла ошибку в первой версии `url-credentials` (схема `[a-z0-9+.-]*`: на `a.a.a.` не укладывалась и в 20 секунд, после ограничения длины схемы — десятые доли секунды). Java 17 сама отсекает часть классических «катастрофических» выражений (`(a+)+$`, `(a|aa)+$`), но не все: `(.*a){25}` упирается в бюджет. Тест гоняет 19 злых входов по 300 КБ через весь базовый список с бюджетом 5 секунд.
- Отвергнуто: ПДн и AWS в базовом списке (решение пользователя; для ФИО нужна модель распознавания имён вроде Presidio, это Python и согласование в контуре); сумма Луна; нумерованные обратимые заглушки (идея из LLM Guard, в версии 1 не нужна); один проход по найденным диапазонам с объединением (последовательное применение даёт тот же результат на нашем списке и проще); отдельный модуль `adapters-masking` (чистый JDK, около ста строк; замена корпоративным средством — замена одного класса); таймаут через отдельный поток (`Future.cancel` регулярное выражение не останавливает); маскирование полей `TestResult` (какие поля и как обходить структуру — шаг 2.6).
- Перенос: PORTING: значение бюджета времени — настройка агента-исполнителя (шаг 2.3). Базовый список согласуется с ИБ (вопросы в конце `docs/masking-rules.md`: состав, ПДн в логах, адреса стендов). Если в контуре потребуется корпоративное средство маскирования, заменяется `RegexMaskingPort`.
- Проверено 2026-11-11: `./gradlew build` зелёный (core 4, adapters-stub 20, adapters-postgres 9, techzone 79, runner 177 тестов). Примеры из документа проходят тестами, обычные строки журнала, стектрейсы и время в миллисекундах не меняются. Проверка 24 намеренными ошибками (шаблоны правил, обработка группы `secret`, пустые совпадения, бюджет времени и перехваты, нумерация шаблонов, копирование списка, границы бюджета): 23 пойманы, одна выжила (условие `from < 0` лишнее, потому что группа, не участвовавшая в совпадении, даёт `start = end = -1`, и проверка `from == to` уже её пропускает; условие удалено); две мутации сначала не скомпилировались из-за ошибки в шаблоне правки, после исправления пойманы; код возвращён побайтно.
- Не покрыто тестами: удаление самого механизма срока (`Deadline` никогда не бросает): мутация не прогонялась, так как «взрывное» выражение тогда не завершилось бы; поведение на реальных логах проектов; ФИО и ПДн (не покрываются по решению).
